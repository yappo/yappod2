# セグメント数に対する字句検索の測定

## 目的

1回の更新が作る小セグメントを自動コンパクションで抑制しても、障害や保守遅延によって一時的に
セグメント数が増える場合があります。この測定は、字句検索の固定費が1・10・100・1000
セグメントでどのように変わるかを確認し、語から対象セグメントを引くキャッシュが必要かを
判断するために実施しました。

この測定は字句検索だけを対象とします。ベクトル検索では各セグメントのANN索引を呼び出すため、
本結果からANN検索の呼び出し回数や処理時間を判断することはできません。

## 条件

| 項目 | 値 |
|---|---|
| 測定日 | 2026年7月31日 |
| 改善前 | `38feef12f1ad24850921e160360772f6c36d2bde`（PR #141適用前） |
| 改善後 | `774237c`（PR #141〜#144適用後） |
| ビルド | CMake `Release` |
| コンパイラー | Apple clang 21.0.0 |
| マシン | MacBook Air、Apple M4、10コア、32 GBメモリー |
| OS | Darwin 25.5.0、arm64 |
| 文書数 | 1セグメントあたり8文書 |
| 文書内容 | `common filler`、100番目ごとのセグメントの先頭文書だけ`common rare filler` |
| 検索条件 | `absenttoken`、`rare`、`common`の一語字句検索、文書単位、上位10件 |
| 実行方法 | 常駐runtime、同時実行数1、各条件を3回事前実行後に101回計測 |
| 時間に含む処理 | runtimeによる検索、上位結果の統合、JSON応答生成 |
| 時間に含まない処理 | 合成索引の生成、manifest検証を含むruntime起動 |

`rare`は100番目ごとのセグメントに存在します。したがって1000セグメントでは10セグメント、
100セグメントでは1セグメント、10セグメントと1セグメントでも最低1セグメントに存在します。
各セグメントの文書数を小さく固定しているため、主にセグメントごとの固定費を観測します。

実行コマンドは次のとおりです。改善前にもベンチマーク実装だけを同じ内容で適用しました。

```sh
./build/v2_segment_search_benchmark \
  --segments <1|10|100|1000> \
  --documents-per-segment 8 \
  --iterations 101
```

単位はミリ秒です。「P50改善倍率」は改善前P50を改善後P50で割った値で、大きいほど高速化しています。

| 10 | 疎な語 | 0.058 | 0.070 | 0.021 | 0.024 | 2.8倍 |
| 10 | 全出現語 | 0.103 | 0.117 | 0.063 | 0.108 | 1.6倍 |
| 100 | 欠損語 | 0.534 | 0.586 | 0.015 | 0.017 | 35.6倍 |
| 100 | 疎な語 | 0.535 | 0.601 | 0.019 | 0.020 | 28.2倍 |
| 100 | 全出現語 | 0.627 | 0.675 | 0.110 | 0.117 | 5.7倍 |

## 1億語エントリーの追加測定

前節の索引は各セグメントに数語しかなく、辞書全体がCPUキャッシュへ収まりやすい条件でした。
語から対象セグメントを引くキャッシュの要否を判断するには不十分だったため、2026年8月1日に
同じ端末で辞書を大きくした追加測定を実施しました。

| 項目 | 値 |
|---|---|
| コミット | `198ea628a18d50ef91e05123c0bbf676ffb5e2a8` |
| セグメント数 | 1000 |
| 文書数 | 1セグメント100文書、合計100,000文書 |
| 生成した固有語 | 1セグメント100,000語、合計100,000,000語エントリー |
| 文書構成 | 1文書1,000固有語。固有語はセグメント間でも重複しない |
| 追加検索語 | 1セグメントだけ、100番目ごとのセグメント、全セグメントに存在する語 |
| 実行方法 | 常駐runtime、同時実行数1、各条件を3回事前実行後に101回計測 |
| 索引容量 | 17,905,606,901バイト |
| 索引生成時間 | 186.005秒 |
| runtime起動時間 | 180.523秒 |
| ピークRSS | 13,905,887,232バイト |

実行コマンドは次のとおりです。

```sh
./build/v2_segment_search_benchmark \
  --segments 1000 \
  --terms-per-segment 100000 \
  --terms-per-document 1000 \
  --iterations 101
```

検索時間の単位はミリ秒です。

| 検索条件 | P50 | P95 |
|---|---:|---:|
| 全セグメントに存在しない語 | 0.241 | 0.316 |
| 1セグメントだけに存在する語 | 0.251 | 0.340 |
| 10セグメントに存在する語 | 0.385 | 0.502 |
| 全セグメントに存在する語 | 0.743 | 1.085 |

小辞書の1000セグメント測定と比べると、欠損語のP95は0.087 msから0.316 ms、
10セグメントに存在する語は0.119 msから0.502 msへ増加しました。セグメントごとの辞書を
大きくすると欠損語と疎な語の探索費用が増えることを確認できました。一方、この合成条件では
キャッシュを使わない状態でも検索P95は1.085 ms以内でした。

ピークRSSには語エントリー配列だけでなく、runtime起動時の検証で参照したmmap領域の
常駐ページも含まれます。語エントリー配列だけを根拠にプロセス全体のメモリーを見積もることは
できません。索引生成物は測定終了後に削除し、空きディスクが測定前の値へ戻ることを確認しました。

CPU、内部SSD、ページフォールト、コンテキストスイッチを追加計測した再実行と、観測処理を
追加していない上記基準値との比較は、
[1億語エントリー・1000セグメント字句検索ベンチマーク](large-dictionary-benchmark-report-2026-08-01.md)
に記録しています。

## 判断

小辞書だけを根拠に、語から対象セグメントを引くキャッシュは不要だとした判断を取り消します。
1億語エントリーの測定により、辞書サイズで欠損語と疎な語の時間が増えることは確認できましたが、
キャッシュの効果とメモリー消費はまだ測っていません。

- 現在確認できたキャッシュなしの上限は、この条件におけるP95 1.085 msです。
- 実運用では語彙の重複率、検索語の繰り返し率、同時実行数、古い文書版の比率が異なります。
- 容量制限付き語―セグメントキャッシュは、同じ語の2回目以降に効果があります。
- セグメント別Bloom filterは、初回の欠損語や疎な語にも効果が見込めますが、偽陽性と固定メモリーを持ちます。

次の判断には、同じ1億語索引でキャッシュなし、容量制限付き語―セグメントキャッシュ、
セグメント別Bloom filterを比較し、検索P50・P95、初回と反復、RSS、世代切替費用を測定する
必要があります。

## 読み取り上の制限

- 合成文書は短く、実運用の文書長と語彙分布を表しません。
- 1億個の生成語はセグメント間でも重複しません。実運用より全体の固有語数が多い極端な条件です。
- 同時実行数は1であり、CPU競合や待ち行列を含みません。
- すべて一時ローカルストレージ上で実行しており、異なるストレージの待ち時間を表しません。
- P50とP95は同一マシン内の改善前後比較に使う値で、他環境の絶対性能を保証しません。
- ベクトル検索と複合検索のANN呼び出し回数は別に設計、測定する必要があります。
