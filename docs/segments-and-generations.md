# セグメント、世代、検索スナップショット

この文書では、文書更新から検索へ反映されるまでの間に、セグメント、世代、検索スナップショットがどのように変化するかを説明します。コマンドの操作方法は[コマンドリファレンス](command-reference.md)、コンパクションを含む運用手順は[索引の更新と保守](index-lifecycle.md)、検索方式の詳細は[検索](search.md)を参照してください。

## 用語

| 用語 | 意味 |
|---|---|
| セグメント | 文書、本文断片、語彙索引、メタデータ索引、ベクトル索引、削除標識を同じ単位で保存する、不変のファイル群です。公開後のセグメントへ追記しません。 |
| 小セグメント | 別のファイル形式ではありません。通常のセグメントを、自動コンパクションのサイズ条件で分類した呼び方です。 |
| 世代 | `manifest.yap2`の`generation`です。公開済み索引状態の通し番号であり、セグメント数ではありません。 |
| マニフェスト | ある世代から参照するセグメントを、古いものから新しいものの順に列挙した`manifest.yap2`です。 |
| 検索スナップショット | 一つのマニフェスト世代を検索用に開いた状態です。一つの検索処理は最後まで同じスナップショットを使います。 |
| コンパクション | 複数の既存セグメントから有効な最新版を選び、新しい適正サイズのセグメント群へ書き直す処理です。 |

「小さい」という表現には、次の二つの異なる判定があります。

| 判定箇所 | 既定の判定 |
|---|---|
| セグメント分割計画 | 最後の分割だけで最大コンポーネントの推定ペイロードが64 MiB未満なら、結合後の各コンポーネントが192 MiB以内である場合に直前の分割へ結合します。 |
| 自動コンパクション | マニフェストに記録された全コンポーネントのファイルサイズ合計が64 MiB未満なら、小セグメントとして数えます。 |

前者は一回の`build`、`update`、`yappo_compact`が小さい末尾を作らないための分割規則です。後者は別々の更新で生じた小セグメントを後から検出する運用規則です。同じ64 MiBでも、比較する値は同じではありません。

## 一回の更新で変わるもの

`update`は1〜10000件の操作を一つのバッチとして受け付けます。1件だけを渡した場合も、最後の公開済みセグメントへ追記せず、新しいセグメントを作ります。

更新は次の順序で進みます。

1. NDJSONまたはJSONを更新操作として解析し、件数と基本構造を検証します。
2. `writer.lock`を取得し、現在の設定、マニフェスト、世代を読みます。
3. 文書ID、本文断片、ベクトル、セグメント容量を検証し、セグメント分割を計画します。
4. `segments/`の新しい一時ディレクトリへ、必要なコンポーネントをすべて書きます。
5. 新しいセグメントのサイズ、チェックサム、内部構造を検証します。
6. 開始時の世代が変わっていないことを確認し、新しいセグメントを追加したマニフェストを原子的に公開します。
7. `writer.lock`を解放します。

公開前の新しいセグメントはマニフェストから参照されないため、検索から見えません。途中で失敗した場合は、公開済み世代を変更せず、作成途中のセグメントを回収します。

一回の更新が適正サイズを超える場合は、複数セグメントへ分割します。複数になっても一回のマニフェスト公開なので、すべて同じ新世代に属します。

## 1件ずつ更新した場合

世代10に二つのセグメントがある状態で、1件更新を4回実行する例は次のとおりです。

```text
世代10: [S1, S2]
世代11: [S1, S2, U11]
世代12: [S1, S2, U11, U12]
世代13: [S1, S2, U11, U12, U13]
世代14: [S1, S2, U11, U12, U13, U14]

自動コンパクション後
世代15: [S1, S2, C15]
```

`U11`から`U14`は各更新が追加したセグメントです。既定では、小セグメントが4個以上連続すると、coreが30秒間隔で行う次の保守確認でコンパクションを開始します。コンパクション後の`C15`は一例であり、入力容量によっては複数セグメントになります。

したがって、セグメント数は更新直後から一定なのではなく、増加と集約を繰り返します。自動コンパクションの目的は、物理セグメント数が小さい更新の回数に比例して増え続けないようにすることです。

`yappo_makeindex update`だけを実行し、`yappod_core`を起動していない場合、自動コンパクションは動きません。`auto_compact_enabled = false`の場合も同じです。必要に応じて`yappo_compact`を実行してください。

## 検索中に更新が公開された場合

一つの検索処理が新旧世代を混ぜて読むことはありません。

```text
検索A: 世代10のスナップショットを取得 ───────── 世代10で完了
更新 : 新セグメントを構築 ─ 検証 ─ 世代11を公開
再読込:                            世代11を検証 ─ 現在値を交換
検索B:                                             世代11で開始
```

再読み込み前に開始した検索は、世代11が公開されても世代10を最後まで使用します。coreは新しいマニフェストとセグメントを正常に開けた場合だけ現在の検索スナップショットを交換します。交換後に始まる検索は世代11を使用します。

HTTP更新では、更新成功後にcoreが直ちに再読み込みを試みます。CLIの`yappo_makeindex update`から更新した場合は、coreの1秒間隔の確認で読み替えます。再読み込みに失敗した場合、coreは旧スナップショットを維持します。HTTPの`503 reload_failed`は、新世代の公開自体が取り消されたことを意味しません。`manifest.yap2`、`/health/ready`、`/metrics`の世代を比較してください。

## 同じ文書IDを更新または削除した場合

更新後も、同じIDの古い文書は旧セグメントに物理的に残ります。新しいスナップショットは、マニフェストを古いセグメントから新しいセグメントの順に読み、文書IDごとに最後の文書または削除標識を有効な状態として記録します。

- 新しい`upsert`があれば、その文書だけを検索結果へ出します。
- 新しい`delete`があれば、それ以前の文書と本文断片を検索結果から除外します。
- コンパクションは対象範囲内の不要な旧版を除去します。

この可視性判定は、検索候補を全件保持してから線形探索するのではなく、スナップショット内の文書IDハッシュを使います。

## コンパクション中の更新と検索

コンパクションは、対象範囲の確定時だけ`writer.lock`を取得し、セグメント構築中は解放します。そのため、構築中も通常の更新を公開できます。公開時に再び`writer.lock`を取得し、選択した隣接範囲が変わっていないことを確認します。

構築中に追加されたセグメントが選択範囲の後ろにあれば、その追加分を残したまま、選択範囲だけを新しいセグメント群へ置き換えます。選択範囲自体が変わっていれば、競合として公開しません。

検索はコンパクション中も旧スナップショットを使用できます。新しいセグメント群とマニフェストを公開しても、検索中の処理が途中で新世代へ移ることはありません。

## セグメントのサイズ規則

`build`、`update`、`yappo_compact`は同じ分割計画を使用します。

| 規則 | 既定値 | 意味 |
|---|---:|---|
| 目標ペイロード | 128 MiB | 各コンポーネントの最大ペイロードが、この値へ近づくよう文書境界で分割します。 |
| 末尾結合の上限 | 192 MiB | 小さい末尾を直前へ結合するとき、各コンポーネントがこの値以内であることを要求します。 |
| 絶対上限 | 256 MiB | 一つのコンポーネントが保存できる最大ペイロードです。 |
| コンパクション入力数 | 最大8セグメント | 一回で置き換える隣接セグメント数の上限です。 |
| コンパクション入力容量 | 原則512 MiB以内 | 選択したセグメントの全コンポーネントファイルサイズ合計の目安です。 |

単独文書はセグメントをまたいで分割しません。単独文書だけでいずれかのコンポーネントが256 MiBを超える場合は、その文書を小さくするか、利用側で複数文書へ分割する必要があります。

## 世代番号の性質と上限

世代番号は符号なし64ビット整数です。最大値は`18446744073709551615`です。

世代値が大きくなっても、検索性能は悪化しません。

- メモリー上とコンポーネントヘッダーでは常に8バイトです。
- 比較と加算は固定時間です。
- セグメントディレクトリ名は最初から20桁のゼロ埋めです。
- `manifest.yap2`では符号なし64ビット整数として常に8バイトで保存します。
- 世代1から現在世代までを順番に走査する処理はありません。

現在世代が最大値に達すると、0へ戻さず、それ以降の`update`と`yappo_compact`を範囲外エラーとして拒否します。最後に公開された世代の検索と取得は継続できます。継続して更新する正式なロールオーバー機能はないため、上限到達時は別ディレクトリへ索引を再構築して切り替える必要があります。マニフェストやコンポーネントヘッダーを手作業で書き換えないでください。

実際には、毎秒100万世代を公開できたとしても上限まで約58万年かかります。更新はセグメント作成、検証、ディスク同期、排他制御を伴うため、世代上限よりセグメント数とコンパクション状態を監視する方が重要です。

マニフェストが参照できるセグメントは最大100000件です。コンパクションが動かず小セグメントが増え続ける場合は、世代上限より先にこの制限へ到達します。

## セグメントと検索スコア

検索は、スナップショットに含まれるすべてのセグメントへ問い合わせます。セグメント数を`S`、内部候補数を`K`とすると、語彙検索とベクトル検索はそれぞれ各セグメントから最大`K`件を集め、全体でも上位`K`件だけを保持します。既定の`K`は100です。

語彙検索のBM25Fは、次の統計を検索スナップショットの全セグメントで共有します。

- 文書数または本文断片数
- 語句の文書頻度
- フィールドの平均長
- Block-Max WANDの上限スコア

文書数、本文断片数、フィールド別総トークン数は世代の読み込み時に一度だけ集計し、メモリに保持します。検索語の文書頻度は各セグメントの辞書検索結果から検索時に合算します。最終スコアとBlock-Max WANDの上限に同じ統計を使用するため、古い文書版を含まない同一の文書集合なら、セグメントの分割方法だけでBM25Fスコアは変わりません。

更新後に旧セグメントへ物理的に残る古い文書版は、候補から除外しても統計には含まれます。そのため、古い版が多い状態では統計に誤差が残り、古い版を除去するコンパクションの前後で語彙スコアや順位が変わる場合があります。ベクトル索引もコンパクション時に再構築するため、近似最近傍探索の候補が変わる場合があります。

複合検索は、全セグメントから集約した語彙候補とベクトル候補をそれぞれ順位付けし、Reciprocal Rank Fusionで統合します。語彙とベクトルの生スコアを直接加算しません。

## 現在の設計で解決する範囲

| 観点 | 現在の状態 |
|---|---|
| 1件更新の不可分性 | 新しいセグメント群とマニフェストを完成後に公開するため、途中状態を検索へ見せません。 |
| 小さい更新の蓄積 | 自動コンパクションで集約し、物理セグメント数が更新回数に比例して増え続けることを防ぎます。 |
| 検索候補メモリー | 語彙とベクトルの結果候補は、それぞれ全体上位`K`件へ制限します。語彙の検索計画は、セグメント数と重複排除後の検索語数に比例する辞書参照を保持します。 |
| BM25Fのセグメント独立性 | 古い文書版を含まない同一文書集合では、全セグメント統計によって分割方法だけではスコアが変わりません。 |
| 旧版の候補除外 | 文書IDハッシュで、現在のスナップショットにおける最新版だけを採用します。 |
| 世代値の増加 | 固定幅整数なので、値の大きさは検索コストへ影響しません。 |

一方で、次は現在も残る性質です。

- 検索はすべてのセグメントへ問い合わせるため、適正サイズのセグメント数が増えれば処理量も増えます。
- 古い文書版もBM25Fの物理統計へ含まれるため、コンパクション前後で完全に同じ順位を保証しません。
- 世代番号自体は更新とコンパクションの公開ごとに増え続けます。

今回のセグメント保守が切り離すのは「更新回数」と「物理セグメント数」です。「総文書量」と「検索処理量」を完全に切り離すものではありません。

## 監視する値

通常運用では、世代番号の大きさではなく、次の値を確認してください。

- `yappod_v2_manifest_segments`
- `yappod_v2_small_segment_run`
- `yappod_v2_auto_compaction_needed`
- `yappod_v2_compaction_state`
- `yappod_v2_compaction_generation`

`yappod_v2_auto_compaction_needed`が複数の確認間隔を過ぎても1のままなら、コンパクション状態、空き容量、ログ、`writer.lock`と`compaction.lock`を確認します。具体的な確認手順は[運用](operations.md)と[監視とメトリクス](observability.md)を参照してください。
