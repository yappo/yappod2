# タスク票と開発作業の運用

この文書は、会話で合意した作業を実装可能な単位へ整理し、GitHub IssueとPRへ引き継ぐ方法を
定めます。PRは作業前の要求票ではなく、合意したタスクを実施した結果の記録として扱います。

## 会話内タスク票とGitHub Issueの使い分け

次の条件をすべて満たす作業は、会話内のタスク票だけで管理します。

- 1つのPRで完了します。
- 同じ作業セッションで実装と検証まで進められます。
- 別の担当者への引き継ぎや、独立した後続課題の追跡を必要としません。

次のいずれかに当てはまる場合はGitHub Issueを作ります。

- 複数PRへ分割します。
- 複数日または複数の作業セッションにまたがります。
- 別の担当者やAIへ引き継ぐ可能性があります。
- いまのPRへ含めない後続課題を追跡する必要があります。

複数PRを束ねるIssueでは、目的と契約境界をIssue本文に一度だけ記録し、各PRは担当する差分と
検証結果を記録します。PRは`Refs #<issue>`で関連付け、全完了条件を確認してからIssueを閉じます。

## タスク票に記録する内容

会話とIssueでは、`.github/ISSUE_TEMPLATE/implementation.md`と同じ観点を使います。

| 項目 | 記録する内容 |
|---|---|
| 目的 | 利用者または保守者にとって何を改善するか |
| 現状 | 現在のソース、テスト、実行結果から確認した事実 |
| 変更対象 | 変更する責務、契約、ファイル群 |
| 対象外 | このタスクで意図的に変更しない事項 |
| 利用者向け契約 | 維持する動作と、変更を許可する動作 |
| 一次ソース | 判断根拠となるソース、テスト、正式文書、再現手順 |
| 検証 | 実行するコマンドと確認する期待結果 |
| 完了条件 | PR、CI、merge、文書更新などの終了判定 |

AIはリポジトリから調査できる現状、関連ファイル、既存テスト、再現手順を先に埋めます。ユーザーへ
確認するのは、互換性、製品動作、対象外、優先順位など、調査だけでは決められない判断です。
「実装を始めてよいか」だけを尋ねる前に、変更対象と残タスクを人間が判断できる文章で提示します。

## 実施中の更新

- 調査で前提が誤っていたと判明した場合は、確定した事実と影響をタスク票へ反映します。
- 利用者向け契約の変更が必要になった場合は、実装を広げる前にユーザー判断を求めます。
- 現在タスクの完了を妨げない別の不具合は、勝手に同じPRへ含めず、Issueの後続項目へ記録します。
- 連続実行が承認されている複数タスクでは、各PRの必須CI成功とmergeを確認してから次のブランチへ
  進みます。追加権限または新しい製品判断が必要な場合だけ停止します。

## PRに残す結果

PR本文は`.github/pull_request_template.md`を使います。

- 「背景」には、このPRが解決するタスク票の一部分を書きます。
- 「変更内容」には、実際に変更した責務と契約を書きます。
- 「検証手順」には、実行したコマンドと結果を書きます。
- 「影響範囲」には、維持した利用者向け契約と、変更した内部契約を書きます。

予定だけをPRへ複製せず、レビュー時点で確認できる実施結果を残します。
