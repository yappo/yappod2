# 10万・100万文書、1億語エントリー、1000セグメント字句検索ベンチマーク

## 概要

このレポートは、字句辞書の大きさ、文書数、セグメント数、同時検索数が検索、索引生成、
runtime起動、メモリー、CPU、内部ストレージへ与える負荷を確認した結果です。外部データは
使用せず、`v2_segment_search_benchmark`が生成する合成索引を使用しました。

最初に、10万文書、1億語エントリー、1000セグメントの同じ条件を2回実行しました。

1. 2026年8月1日の基準測定では、ベンチマーク自身が出力する時間とRSSだけを記録しました。
2. 同日の観測付き測定では、基準測定と同じ入力に`/usr/bin/time -lp`と5秒間隔の`iostat`を
   追加し、CPU、ページ、コンテキストスイッチ、内部SSD負荷を記録しました。

観測処理が測定対象へ影響する可能性があるため、検索時間の基準値は1回目を維持し、
2回目は負荷の説明と再現性確認に使用します。

その後、1文書の生成語数を1000語から100語へ減らし、1セグメントの文書数を100文書から
1000文書へ増やしました。語エントリー総数とセグメント数を変えず、合計100万文書にした条件を
非観測と観測付きで測定しています。観測付き測定で作成した索引は削除せず、同じ索引を常駐coreへ
開いて同時数1〜64のHTTP字句検索も測定しました。

## 10万文書測定の実行方法

基準測定は次のコマンドだけを実行しました。

```sh
./build/v2_segment_search_benchmark \
  --segments 1000 \
  --terms-per-segment 100000 \
  --terms-per-document 1000 \
  --iterations 101
```

観測付き測定では、別プロセスの`iostat`を5秒間隔で実行し、ベンチマークを
`/usr/bin/time -lp`で起動しました。

```sh
iostat -w 5

/usr/bin/time -lp \
  ./build/v2_segment_search_benchmark \
  --segments 1000 \
  --terms-per-segment 100000 \
  --terms-per-document 1000 \
  --iterations 101
```

`iostat`は内部SSDとシステム全体のCPUを観測します。ベンチマークプロセスだけのI/Oではなく、
同時刻に動いたOSと他プロセスのI/Oも含みます。`/usr/bin/time`はベンチマークプロセスと
その子プロセスを対象とします。このベンチマークは子プロセスを起動しません。

| フェーズ | サンプル数 | 平均転送量 | 転送量範囲 | 平均IOPS | IOPS範囲 | 平均転送サイズ |

| 索引生成の安定区間 | 22 | 92.83 MB/s | 90.96〜97.72 MB/s | 177.5 | 116〜491 | 641.73 KB |

索引生成では、セグメントファイルの書込みに加え、descriptorへ記録するチェックサム計算のための

## 10万文書測定の解釈

### 検索ホットパス

1000セグメント、1億生成語エントリーでも、キャッシュなしの字句検索P95は欠損語0.316 ms、
1%出現語0.502 ms、全セグメント共通語1.085 msでした。大辞書化によって欠損語と疎な語の
辞書探索費用は小辞書より増えましたが、絶対時間は1 ms前後以内です。

語から対象セグメントを引くキャッシュまたはBloom filterの効果を判断する場合、この値が
短縮可能時間の上限になります。実装複雑性、世代切替、メモリー増加と比較して判断する必要があります。

### runtime起動

検索要求は高速ですが、runtime起動は基準180.523秒、観測付き178.776秒でした。
I/O活動区間は平均約171 MB/s、約2,924 IOPSで、ピークRSSは約14.26 GBです。
大規模索引では、検索ごとの辞書探索より、起動時の全セグメント検証と語エントリー配列の展開が
運用上の大きな負荷です。

この起動時間は検索要求ごとには発生しません。常駐runtimeを再利用し、世代更新時は変更のない
セグメントを再利用する現在の設計を前提に評価する必要があります。

### 索引生成

1億語エントリーの生成は約185秒で、内部SSDは安定区間で約93 MB/sでした。
各セグメントを生成して書き終えた後に本文バッファを解放しているため、1000セグメント分の
生成本文を同時に保持しません。セグメント数の増加による生成速度の継続的な低下は観測しませんでした。

## 100万文書測定

### 目的と入力差分

10万文書測定と同じ1億生成語エントリー、同じ1000セグメントを維持し、文書数だけを10倍に
しました。これにより、辞書とposting総数をほぼ同じにしたまま、文書テーブルと文書ファイルの
増加による影響を比較します。

| 項目 | 10万文書 | 100万文書 |
|---|---:|---:|
| セグメント数 | 1000 | 1000 |
| 1セグメントの文書数 | 100 | 1000 |
| 合計文書数 | 100,000 | 1,000,000 |
| 1文書の生成固有語 | 1000語 | 100語 |
| 1セグメントの生成固有語 | 100,000語 | 100,000語 |
| 生成語エントリー総数 | 100,000,000 | 100,000,000 |
| 生成本文の標準的な長さ | 13,999バイト | 1,399バイト |
| 合成索引の論理容量 | 17,905,606,901バイト | 17,946,537,837バイト |

各生成語は13バイトで、語間に1バイトの空白があります。100万文書条件の標準的な本文は
100語で1,399バイトです。各セグメントの先頭文書には全セグメント共通語が加わるため
1,406バイトとなり、100番目ごとのセグメントではさらに1%出現語が加わって1,411バイトに
なります。表の索引容量には文書ID、コンポーネントヘッダー、辞書、postingなども含みます。

### 実行方法

非観測の基準測定は次のコマンドだけを実行しました。`documents-per-segment`は、
`terms-per-segment / terms-per-document`から1000と計算されます。

```sh
./build/v2_segment_search_benchmark \
  --segments 1000 \
  --terms-per-segment 100000 \
  --terms-per-document 100 \
  --iterations 101
```

観測付き測定では5秒間隔の`iostat`と`/usr/bin/time -lp`を使用しました。高負荷測定へ
同じ索引を渡すため、事前に存在しない測定専用ディレクトリーを`--retain-index`へ指定しました。
次の`MEASUREMENT_DIR`は任意の測定専用領域を表すプレースホルダーで、実際のローカルパスでは
ありません。

```sh
iostat -w 5

/usr/bin/time -lp \
  ./build/v2_segment_search_benchmark \
  --segments 1000 \
  --terms-per-segment 100000 \
  --terms-per-document 100 \
  --iterations 101 \
  --retain-index MEASUREMENT_DIR/index
```

測定開始前のデータボリューム空き容量は152 GB、メモリー空き率は73%、1分load averageは
2.19でした。観測付き索引を保持した後の空き容量は約134 GBでした。

## 100万文書索引の高負荷検索

### 測定構成

観測付き測定で保持した100万文書、1000セグメントの同じ索引をcoreへ1回だけオープンし、
frontを通してHTTP字句検索を実行しました。ANN、ベクトル検索、文書更新、コンパクションは
この測定に含みません。

| 項目 | 値 |
|---|---:|
| core worker threads | 16 |
| front worker threads | 16 |
| 通常測定の`max_inflight` | 16 |
| `max_inflight_bytes` | 64 MiB |
| 要求数 | 各同時数12,000件 |
| 同時数 | 1、4、8、16、32、64 |
| 検索方式 | 字句検索、文書単位 |
| 検索語 | 全セグメント共通語1語と、固有語16語のOR検索 |
| 返却上限 | 100件 |
| TCP | 要求ごとに新規接続、応答後に切断 |
| 段階間の待機 | 31秒 |

負荷生成器は各要求の応答コードと時間を記録し、成功要求だけからP50、P95、P99を算出します。
処理量は成功、503 `overloaded`、通信失敗を含む全要求数を区間実時間で割ります。通常測定では
通信失敗と503が0件であることを確認しました。

各段階で負荷生成器を`/usr/bin/time -lp`から起動し、coreとfrontの累積CPU時間とRSSを
段階の前後に取得しました。高同時数の区間は約5秒で終わるため、`iostat`だけは1秒間隔へ
変更しました。測定手段は100万文書生成と同じですが、間隔が異なるため両表の値は直接比較しません。

検索文は`common`と`t000000000000`から`t000000000015`までの16語です。各同時数では次の形で
実行し、同時数1〜16には`--require-all-success`を追加しました。

```sh
iostat -w 1

/usr/bin/time -lp \
  ./build/v2_load_probe \
  --port FRONT_PORT \
  --lexical-request MEASUREMENT_DIR/lexical-request.json \
  --core-pid CORE_PID \
  --front-pid FRONT_PID \
  --requests 12000 \
  --concurrency CONCURRENCY
```

`FRONT_PORT`、`CORE_PID`、`FRONT_PID`は測定時の値へ置き換えます。ローカルの実値は個人情報では
ありませんが、再現性に不要で別環境では変わるため記録していません。

### 同一端末から負荷を生成する制約

frontの実応答は`Connection: close`を返します。この端末の一時ポート範囲は49152〜65535の
16,384個で、TCP MSLは15秒でした。最初の予備測定で、同時数4の60,000件中14,702件が
成功した後、45,298件が通信失敗となりました。coreとfrontは生存し、503は0件でした。
この試行はサーバー性能値として無効なため、結果表には含めません。

最終測定では各段階を12,000件に制限し、2 MSLを超える31秒を段階間に空けました。
本番相当の長時間負荷を1台から生成する場合は、複数の負荷生成ホストまたは送信元IPを使用するか、
frontが接続再利用を提供した後にkeep-alive対応クライアントを使用する必要があります。

### 過負荷保護プロファイル

この節の`worker_threads`は測定時点の旧設定名です。現在はfront接続、core接続、core検索計算を
`front_io_threads`、`core_io_threads`、`core_search_threads`へ分離しており、数値を比較するときは測定時の
単一設定だったことに注意してください。

`worker_threads=16`と`max_inflight=16`が同じ場合、同時数32と64でも503は発生しませんでした。
16本を超える接続は処理枠を取得する前のソケット待ち行列へ並ぶためです。待ち行列ではなく
明示的な503で保護する構成を確認するため、同じcoreへ`worker_threads=16`、
`max_inflight=4`のfrontを追加し、同時数16で12,000件を送りました。

| 成功 | 503 `overloaded` | 通信失敗 | 成功率 | 503率 | 成功P50 | 成功P95 | 成功P99 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 446 | 11,554 | 0 | 3.72% | 96.28% | 3.853 ms | 6.135 ms | 7.939 ms |

全12,000応答は0.488秒、拒否を含む応答処理量は24,597.57 req/sでした。この処理量の大半は
検索を実行しない503であり、検索能力として扱いません。区間が1秒未満のため、`iostat`は
終了時の部分サンプル1件しかなく、安定したCPU/I/O値としては採用しません。coreとfrontの
CPU増分は合計1.77秒でした。

この結果は`max_inflight`を小さくすれば遅延上昇を拒否へ置き換えられることを示しますが、
4では今回の突発負荷の96%を拒否します。本番値は許容P95/P99、再試行方針、目標成功率を先に
決め、4〜8付近を段階的に測って選ぶ必要があります。

### 次に行う高負荷試験

今回の結果から、次の順で試験を追加するのが適切です。

1. 複数の負荷生成元を用意し、同時数8、約1,600 req/sから30分以上の持続試験を行います。
   約1,600 req/sは今回のピーク約2,300 req/sの70%で、温度、メモリー圧力、P99の時間変化を
   観測しやすい開始点です。
2. `max_inflight`を4、6、8、12で比較し、成功率とP99の運用目標から値を決めます。
3. 検索だけの基準を固定した後、文書更新を並行する混合負荷を別測定にします。更新公開時刻、
   世代切替時間、検索P99、検索結果の世代整合性、コンパクション発生有無を記録します。
4. cold start、通常運転、更新直後を分離します。約180秒のruntime起動I/Oを検索処理量へ
   混ぜないようにします。
5. ANNを実装・有効化した後は、字句検索と混ぜず、ANN単独の同時数とセグメント数を先に測ります。

## 制限事項

- 合成語は固定長ASCIIで、自然言語の語長、正規化費用、語彙重複率を再現しません。
- 生成語は各文書に1回だけ現れ、長い投稿リストを持つ高頻度語の分布を再現しません。
- 10万・100万文書の単独検索基準は同時実行数1です。高負荷測定は別の17語・100件応答条件で、
  単独検索表のP50/P95と直接比較できません。
- `iostat`は索引生成とruntime起動で5秒間隔、高負荷検索で1秒間隔のシステム全体値です。
  プロセス単独の読込みと書込みを分離できません。
- 高負荷測定は段階ごとに約5〜30秒で、温度上昇、長時間のメモリー圧力、持続的なP99を
  評価していません。
- HTTP負荷は同一端末から要求ごとに新しいTCP接続を作りました。複数クライアントや
  広域ネットワークの遅延を再現しません。
- 文書更新、世代切替、コンパクション、ANNは高負荷測定に含みません。
- デスクトップ上の他プロセスを停止していないため、CPUとI/Oに小さな外乱を含みます。
- 基準測定と観測付き測定は同じ端末の別実行であり、CPU温度とクロックを固定していません。
- 絶対時間はこの端末とソフトウェア版に固有で、別環境の性能保証ではありません。

## 再測定時に保存する情報

比較可能性を保つため、再測定では次を保存します。ただし個人識別情報と絶対パスは保存しません。

- Gitコミット、CMakeビルド種別、コンパイラー版
- MacのModel Identifier、SoC、コア構成、物理メモリー、OS版
- ストレージの内蔵・SSD・接続方式・ファイルシステム・容量・空き容量
- セグメント数、文書数、生成語数、語長、語の重複規則
- 事前実行回数、計測回数、同時実行数
- 索引容量、生成時間、runtime起動時間、検索P50・P95、RSS
- process user/system CPU時間、page faults、swap、context switches
- `iostat`間隔、CPU user/system/idle、転送量、IOPS
- 観測処理の有無と、観測なしの基準値
