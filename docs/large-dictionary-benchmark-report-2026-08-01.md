# 1億語エントリー・1000セグメント字句検索ベンチマーク

## 概要

このレポートは、字句辞書の大きさとセグメント数が検索、索引生成、runtime起動、メモリー、
CPU、内部ストレージへ与える負荷を確認した結果です。外部データは使用せず、
`v2_segment_search_benchmark`が生成する合成索引を使用しました。

同じ条件を2回実行しています。

1. 2026年8月1日の基準測定では、ベンチマーク自身が出力する時間とRSSだけを記録しました。
2. 同日の観測付き測定では、基準測定と同じ入力に`/usr/bin/time -lp`と5秒間隔の`iostat`を
   追加し、CPU、ページ、コンテキストスイッチ、内部SSD負荷を記録しました。

観測処理が測定対象へ影響する可能性があるため、検索時間の基準値は1回目を維持し、
2回目は負荷の説明と再現性確認に使用します。

## 個人情報を含めないための方針

レポートには再現性に必要な機種区分と一般的なハードウェア情報だけを記録します。
次の情報は収集結果へ含めません。

- ホスト名とコンピューター名
- ユーザー名
- シリアル番号とハードウェアUUID
- ボリューム名とボリュームUUID
- リポジトリ、ホームディレクトリ、一時ディレクトリの絶対パス
- ディスク上の利用者ファイル名

## 実行方法

基準測定は次のコマンドだけを実行しました。

```sh
./build/v2_segment_search_benchmark \
  --segments 1000 \
  --terms-per-segment 100000 \
  --terms-per-document 1000 \
  --iterations 101
```

観測付き測定では、別プロセスの`iostat`を5秒間隔で実行し、ベンチマークを
`/usr/bin/time -lp`で起動しました。

```sh
iostat -w 5

/usr/bin/time -lp \
  ./build/v2_segment_search_benchmark \
  --segments 1000 \
  --terms-per-segment 100000 \
  --terms-per-document 1000 \
  --iterations 101
```

`iostat`は内部SSDとシステム全体のCPUを観測します。ベンチマークプロセスだけのI/Oではなく、
同時刻に動いたOSと他プロセスのI/Oも含みます。`/usr/bin/time`はベンチマークプロセスと
その子プロセスを対象とします。このベンチマークは子プロセスを起動しません。

## 観測付き測定結果

### 時間と検索性能

| 項目 | 基準測定 | 観測付き測定 | 基準比 |
|---|---:|---:|---:|
| 索引生成時間 | 186.005秒 | 184.920秒 | -0.58% |
| runtime起動時間 | 180.523秒 | 178.776秒 | -0.97% |
| ピークRSS | 13.91 GB | 14.26 GB | +2.58% |

| 検索条件 | 基準P50 | 観測付きP50 | 基準P95 | 観測付きP95 |
|---|---:|---:|---:|---:|
| 欠損語 | 0.241 | 0.231 | 0.316 | 0.339 |
| 単一セグメント語 | 0.251 | 0.243 | 0.340 | 0.333 |
| 1%出現語 | 0.385 | 0.370 | 0.502 | 0.549 |
| 全セグメント共通語 | 0.743 | 0.713 | 1.085 | 1.085 |

索引生成とruntime起動は、観測付き測定の方がそれぞれ0.58%と0.97%短くなりました。
検索P95の差は-2.06%〜+9.36%です。処理時間が1 ms前後以下であるため、OSスケジューリングや
クロック取得の揺れが比率を大きく見せます。観測処理による一方向の性能低下は確認できませんが、
観測に影響がないと保証する結果ではありません。

### プロセスCPUと実行統計

`/usr/bin/time -lp`の結果です。

| 項目 | 値 |
|---|---:|
| 全体実時間 | 365.16秒 |
| user CPU時間 | 330.32秒 |
| system CPU時間 | 14.22秒 |
| 平均プロセスCPU使用率 | 94.35% |
| 命令リタイア数 | 3,724,419,482,547 |
| CPUサイクル | 1,413,610,543,106 |
| 1サイクルあたり命令数 | 約2.63 |
| page reclaims | 2,325,772 |
| page faults | 1,010,166 |
| swap | 0 |
| voluntary context switches | 22,162 |
| involuntary context switches | 450,784 |
| maximum resident set size | 14,264,729,600バイト |
| peak memory footprint | 7,607,341,000バイト |

平均プロセスCPU使用率は`(user CPU時間 + system CPU時間) / 実時間`で算出しました。
約94%は10コア全体の94%ではなく、論理CPU 1個を100%とするプロセスCPU時間の表現です。
索引生成とruntime起動は、全体として1論理CPUをほぼ使い切る単一処理寄りの動作でした。

`maximum resident set size`と`peak memory footprint`はmacOSが異なる定義で報告する値です。
前者は常駐ページの最大、後者はメモリー圧力計算で使う物理フットプリントであり、同じ値にはなりません。

### システム全体のCPU負荷

`iostat`の5秒サンプルから、フェーズが安定している区間を集計しました。

| フェーズ | サンプル数 | user | system | idle | 1分load average |
|---|---:|---:|---:|---:|---:|
| 索引生成 | 22 | 14.8% | 2.2% | 82.9% | 2.34 |
| runtime起動中のI/O活動区間 | 32 | 13.8% | 3.0% | 83.0% | 2.39 |

このCPU値は10コアを合計したシステム全体の値で、OSと他プロセスを含みます。
プロセスCPU時間と合わせると、ベンチマーク自身はほぼ1論理CPUを使用し、残りのuser負荷は
同時に動いていたOSまたは他プロセスによるものと解釈できます。

検索4条件の計測部分は合計時間が短く、5秒間隔の`iostat`では独立したCPU区間として
分離できません。検索時間自体はベンチマーク内の単調時計で要求ごとに測っています。

### 内部SSD負荷

| フェーズ | サンプル数 | 平均転送量 | 転送量範囲 | 平均IOPS | IOPS範囲 | 平均転送サイズ |
|---|---:|---:|---:|---:|---:|---:|
| 索引生成の安定区間 | 22 | 92.83 MB/s | 90.96〜97.72 MB/s | 177.5 | 116〜491 | 641.73 KB |
| runtime起動中のI/O活動区間 | 32 | 170.89 MB/s | 126.71〜298.63 MB/s | 2,923.8 | 908〜5,086 | 100.35 KB |

索引生成では、セグメントファイルの書込みに加え、descriptorへ記録するチェックサム計算のための
読込みも発生します。runtime起動では既存ファイルを書き換えず、manifestと各コンポーネントを
読み込んで検証します。このため、生成は大きな転送単位、runtime起動は小さな転送単位と高いIOPSを
示しました。

`iostat`はディスク全体の読込みと書込みを合算して表示するため、上の値からベンチマークだけの
正確な読込バイト数と書込バイト数を分離できません。`/usr/bin/time`がこのmacOS環境で報告した
block input/output operationsはどちらも0であり、I/O量の根拠には使用していません。

## 結果の解釈

### 検索ホットパス

1000セグメント、1億生成語エントリーでも、キャッシュなしの字句検索P95は欠損語0.316 ms、
1%出現語0.502 ms、全セグメント共通語1.085 msでした。大辞書化によって欠損語と疎な語の
辞書探索費用は小辞書より増えましたが、絶対時間は1 ms前後以内です。

語から対象セグメントを引くキャッシュまたはBloom filterの効果を判断する場合、この値が
短縮可能時間の上限になります。実装複雑性、世代切替、メモリー増加と比較して判断する必要があります。

### runtime起動

検索要求は高速ですが、runtime起動は基準180.523秒、観測付き178.776秒でした。
I/O活動区間は平均約171 MB/s、約2,924 IOPSで、ピークRSSは約14.26 GBです。
大規模索引では、検索ごとの辞書探索より、起動時の全セグメント検証と語エントリー配列の展開が
運用上の大きな負荷です。

この起動時間は検索要求ごとには発生しません。常駐runtimeを再利用し、世代更新時は変更のない
セグメントを再利用する現在の設計を前提に評価する必要があります。

### 索引生成

1億語エントリーの生成は約185秒で、内部SSDは安定区間で約93 MB/sでした。
各セグメントを生成して書き終えた後に本文バッファを解放しているため、1000セグメント分の
生成本文を同時に保持しません。セグメント数の増加による生成速度の継続的な低下は観測しませんでした。

## 制限事項

- 合成語は固定長ASCIIで、自然言語の語長、正規化費用、語彙重複率を再現しません。
- 生成語は各文書に1回だけ現れ、長い投稿リストを持つ高頻度語の分布を再現しません。
- 検索は同時実行数1です。複数検索のCPU競合、ロック待ち、待ち行列を測っていません。
- `iostat`は5秒間隔かつシステム全体の値です。短い検索区間やプロセス単独のI/Oを分離できません。
- デスクトップ上の他プロセスを停止していないため、CPUとI/Oに小さな外乱を含みます。
- 基準測定と観測付き測定は同じ端末の別実行であり、CPU温度とクロックを固定していません。
- 絶対時間はこの端末とソフトウェア版に固有で、別環境の性能保証ではありません。
