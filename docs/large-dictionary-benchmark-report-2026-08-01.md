# 100万文書索引のserver/client並列負荷ベンチマーク

## 概要

このレポートの主目的は、100万文書、1000セグメントの索引に対して、yappodのserver
`worker_threads`とclient同時数をそれぞれ複数段階へ変え、各組み合わせのRPS、P50、P95、
P99、CPU、メモリー、I/O負荷を測定することです。

serverは1、2、4、8、16、32、64、128 worker、clientは1、2、4、8、16、32、64、128、
256同時の合計72条件を測りました。各条件は12,000要求で、合計864,000要求がすべて成功しました。
絶対最高値はserver=32、client=256の2,537.954 RPSですが、処理量とレイテンシの均衡点は
server=16、client=16の2,468.561 RPS、P95 12.266 msでした。

`max_inflight`を4、8、16へ変えた過負荷保護の比較も行いました。

10万文書と100万文書の索引生成、runtime起動、単一検索の測定結果は、負荷試験で使用した索引の
容量と基礎性能を説明するための補助情報として残しています。外部データは使用せず、
`v2_segment_search_benchmark`が生成する合成索引を使用しました。

### この端末での推奨パラメーター

処理量とレイテンシを両方考慮した推奨値は、server `worker_threads=16`、client同時数16、
`max_inflight=16`です。2,468.561 RPS、P95 12.266 msで、今回の絶対最高RPSの97.3%を
処理しました。

| 目的 | server worker | client同時数 | max_inflight | RPS | P95 | 判断 |
|---|---:|---:|---:|---:|---:|---|
| 処理量と遅延の均衡 | 16 | 16 | 16 | 2,468.561 | 12.266 ms | この端末での推奨値です |
| レイテンシを優先 | 8 | 16 | 8 | 2,247.654 | 9.017 ms | 推奨値よりRPSは約9%低い一方、CPU余力を残します |
| 絶対RPSだけを最大化 | 32 | 256 | 32 | 2,537.954 | 87.672 ms | P99も302.782 msまで増えるため推奨しません |

server=16のまま`max_inflight`だけを8へ下げると、client同時数16の短いバーストで91.99%を
503拒否しました。したがって、今回の条件では`max_inflight=16`を維持するのが適切です。
`max_inflight=8`は、503を受けたclientが指数バックオフ付きで再試行でき、成功率よりtail latencyを
優先する場合だけ候補にします。

この推奨値は、Apple M4 10コア、100万文書、1000セグメント、17語OR検索、返却上限100件、
短時間負荷という今回の条件に対するものです。別のCPU、検索語分布、返却件数、持続負荷へ
そのまま適用できる一般的な最適値ではありません。

## 10万文書測定の実行方法

基準測定は次のコマンドだけを実行しました。

```sh
./build/v2_segment_search_benchmark \
  --segments 1000 \
  --terms-per-segment 100000 \
  --terms-per-document 1000 \
  --iterations 101
```

観測付き測定では、別プロセスの`iostat`を5秒間隔で実行し、ベンチマークを
`/usr/bin/time -lp`で起動しました。

```sh
iostat -w 5

/usr/bin/time -lp \
  ./build/v2_segment_search_benchmark \
  --segments 1000 \
  --terms-per-segment 100000 \
  --terms-per-document 1000 \
  --iterations 101
```

`iostat`は内部SSDとシステム全体のCPUを観測します。ベンチマークプロセスだけのI/Oではなく、
同時刻に動いたOSと他プロセスのI/Oも含みます。`/usr/bin/time`はベンチマークプロセスと
その子プロセスを対象とします。このベンチマークは子プロセスを起動しません。

## 10万文書測定の解釈

### 検索ホットパス

1000セグメント、1億生成語エントリーでも、キャッシュなしの字句検索P95は欠損語0.316 ms、
1%出現語0.502 ms、全セグメント共通語1.085 msでした。大辞書化によって欠損語と疎な語の
辞書探索費用は小辞書より増えましたが、絶対時間は1 ms前後以内です。

語から対象セグメントを引くキャッシュまたはBloom filterの効果を判断する場合、この値が
短縮可能時間の上限になります。実装複雑性、世代切替、メモリー増加と比較して判断する必要があります。

### runtime起動

検索要求は高速ですが、runtime起動は基準180.523秒、観測付き178.776秒でした。
I/O活動区間は平均約171 MB/s、約2,924 IOPSで、ピークRSSは約14.26 GBです。
大規模索引では、検索ごとの辞書探索より、起動時の全セグメント検証と語エントリー配列の展開が
運用上の大きな負荷です。

この起動時間は検索要求ごとには発生しません。常駐runtimeを再利用し、世代更新時は変更のない
セグメントを再利用する現在の設計を前提に評価する必要があります。

### 索引生成

1億語エントリーの生成は約185秒で、内部SSDは安定区間で約93 MB/sでした。
各セグメントを生成して書き終えた後に本文バッファを解放しているため、1000セグメント分の
生成本文を同時に保持しません。セグメント数の増加による生成速度の継続的な低下は観測しませんでした。

## 100万文書測定

### 目的と入力差分

10万文書測定と同じ1億生成語エントリー、同じ1000セグメントを維持し、文書数だけを10倍に
しました。これにより、辞書とposting総数をほぼ同じにしたまま、文書テーブルと文書ファイルの
増加による影響を比較します。

| 項目 | 10万文書 | 100万文書 |
|---|---:|---:|
| セグメント数 | 1000 | 1000 |
| 1セグメントの文書数 | 100 | 1000 |
| 合計文書数 | 100,000 | 1,000,000 |
| 1文書の生成固有語 | 1000語 | 100語 |
| 1セグメントの生成固有語 | 100,000語 | 100,000語 |
| 生成語エントリー総数 | 100,000,000 | 100,000,000 |
| 生成本文の標準的な長さ | 13,999バイト | 1,399バイト |
| 合成索引の論理容量 | 17,905,606,901バイト | 17,946,537,837バイト |

各生成語は13バイトで、語間に1バイトの空白があります。100万文書条件の標準的な本文は
100語で1,399バイトです。各セグメントの先頭文書には全セグメント共通語が加わるため
1,406バイトとなり、100番目ごとのセグメントではさらに1%出現語が加わって1,411バイトに
なります。表の索引容量には文書ID、コンポーネントヘッダー、辞書、postingなども含みます。

### 実行方法

非観測の基準測定は次のコマンドだけを実行しました。`documents-per-segment`は、
`terms-per-segment / terms-per-document`から1000と計算されます。

```sh
./build/v2_segment_search_benchmark \
  --segments 1000 \
  --terms-per-segment 100000 \
  --terms-per-document 100 \
  --iterations 101
```

観測付き測定では5秒間隔の`iostat`と`/usr/bin/time -lp`を使用しました。高負荷測定へ
同じ索引を渡すため、事前に存在しない測定専用ディレクトリーを`--retain-index`へ指定しました。
次の`MEASUREMENT_DIR`は任意の測定専用領域を表すプレースホルダーで、実際のローカルパスでは
ありません。

```sh
iostat -w 5

/usr/bin/time -lp \
  ./build/v2_segment_search_benchmark \
  --segments 1000 \
  --terms-per-segment 100000 \
  --terms-per-document 100 \
  --iterations 101 \
  --retain-index MEASUREMENT_DIR/index
```

測定開始前のデータボリューム空き容量は152 GB、メモリー空き率は73%、1分load averageは
2.19でした。観測付き索引を保持した後の空き容量は約134 GBでした。

frontを通してHTTP字句検索を実行しました。ANN、ベクトル検索、文書更新、コンパクションは

### 初回測定時点での次の高負荷試験

今回の結果から、次の順で試験を追加するのが適切です。

1. 複数の負荷生成元を用意し、同時数8、約1,600 req/sから30分以上の持続試験を行います。

   観測しやすい開始点です。
2. `max_inflight`を4、6、8、12で比較し、成功率とP99の運用目標から値を決めます。
3. 検索だけの基準を固定した後、文書更新を並行する混合負荷を別測定にします。更新公開時刻、
   世代切替時間、検索P99、検索結果の世代整合性、コンパクション発生有無を記録します。
4. cold start、通常運転、更新直後を分離します。約180秒のruntime起動I/Oを検索処理量へ
   混ぜないようにします。
5. ANNを実装・有効化した後は、字句検索と混ぜず、ANN単独の同時数とセグメント数を先に測ります。

## server/client並列数マトリクス

### 測定方法

観測付き測定で保持した100万文書、1000セグメントの索引を、server設定ごとにcoreへ開き直しました。
coreとfrontには同じ`worker_threads`を設定し、通常マトリクスでは`max_inflight`も同じ値にしました。

|---|---|
| `worker_threads` | 1、2、4、8、16、32、64、128 |

| 組合せ数 | 72 |
| 要求数 | 各組合せ12,000件、合計864,000件 |
| 検索方式 | 字句検索、文書単位 |

除くためのものです。単一同時数で分離前後を確認した差は約0.4%でした。各セルの前には65秒待ち、

### server worker数の判断

絶対最高値は`worker_threads=32`、client=256の2,537.954 RPSですが、P95は87.672 ms、
P99は302.782 msです。`worker_threads=16`、client=16は2,468.561 RPSで、絶対最高値の
97.3%をP95 12.266 msで処理しました。この端末と検索条件では16/16が処理量と遅延の
均衡点です。

`worker_threads=32`、client=16は2,464.886 RPSで16/16とほぼ同じです。workerを倍にしても
CPUコア数は変わらないため、低いclient同時数では利点がありません。64/16は2,419.180 RPS、
128/16は2,298.807 RPSまで下がりました。`worker_threads=128`はclient=1でも384.562 RPSで、
16の426.625 RPSより約9.9%低く、固定的なスレッド管理費も見えます。

`worker_threads=32`は設定上限ではありません。設定値の入力範囲は現在1〜1024ですが、
この端末では16付近が実用点、32は低遅延を犠牲にした絶対RPS確認用、64以上は過剰です。

`max_inflight=4`は成功P95を4.4〜5.5 msへ抑えますが、92.46〜96.25%を拒否します。
`max_inflight=8`はclient=8なら全成功ですが、client=16以上の瞬間的な飽和では91.99%以上を

選ぶ値です。今回の結果だけで4または8を既定値にすると拒否が多すぎます。成功率を優先するなら16、
厳しいtail latencyを優先してclientが指数バックオフ付き再試行へ対応できる場合は8を候補にし、
実際のSLOと到着分布で再測定する必要があります。

## server/client負荷試験からの次の試験

1. 別の負荷生成ホストから、16/16の約70%にあたる1,700 req/s前後を30分以上維持し、温度、
   RPS、P95/P99、CPU、メモリー圧力、swap、503を時系列で記録します。
2. 実運用の再試行方針と成功率SLOを決めた後、`max_inflight=8`と16を実データの到着分布で
   比較します。固定同時数の短いバーストだけで既定値を変更しません。
3. 検索基準を固定してから文書更新を混ぜ、更新公開時間、検索P99、世代整合性、コンパクション、
   CPU・I/Oを同時に測ります。
4. 100万文書で増えたruntime RSSを、同一コミット、cold cache、複数回反復で切り分けます。
5. ANNは別測定とし、字句検索のworker設定判断へ混ぜません。

## 制限事項

- 合成語は固定長ASCIIで、自然言語の語長、正規化費用、語彙重複率を再現しません。
- 生成語は各文書に1回だけ現れ、長い投稿リストを持つ高頻度語の分布を再現しません。
- 10万・100万文書の単独検索基準は同時実行数1です。高負荷測定は別の17語・100件応答条件で、
  単独検索表のP50/P95と直接比較できません。
- `iostat`は索引生成とruntime起動で5秒間隔、高負荷検索で1秒間隔のシステム全体値です。
  プロセス単独の読込みと書込みを分離できません。
- 高負荷測定は段階ごとに約5〜30秒で、温度上昇、長時間のメモリー圧力、持続的なP99を
  評価していません。
- HTTP負荷は同一端末から要求ごとに新しいTCP接続を作りました。正式測定では
  client→frontをIPv4、front→coreをIPv6 loopbackへ分離しています。複数クライアントや
  広域ネットワークの遅延は再現しません。
- 文書更新、世代切替、コンパクション、ANNは高負荷測定に含みません。
- 基準測定と観測付き測定は同じ端末の別実行であり、CPU温度とクロックを固定していません。
- 絶対時間はこの端末とソフトウェア版に固有で、別環境の性能保証ではありません。

## 再測定時に保存する情報

比較可能性を保つため、再測定では次を保存します。ただし個人識別情報と絶対パスは保存しません。

- Gitコミット、CMakeビルド種別、コンパイラー版
- MacのModel Identifier、SoC、コア構成、物理メモリー、OS版
- ストレージの内蔵・SSD・接続方式・ファイルシステム・容量・空き容量
- セグメント数、文書数、生成語数、語長、語の重複規則
- 事前実行回数、計測回数、同時実行数
- 索引容量、生成時間、runtime起動時間、検索P50・P95、RSS
- process user/system CPU時間、page faults、swap、context switches
- `iostat`間隔、CPU user/system/idle、転送量、IOPS
- 観測処理の有無と、観測なしの基準値
